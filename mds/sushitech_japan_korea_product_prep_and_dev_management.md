# SusHi Tech 준비 체크리스트 + 한일 서비스 개발 관리 문서

## 1. 문서 목적
이 문서는 아래 2가지를 동시에 달성하기 위한 내부 기준 문서다.

1. SusHi Tech Tokyo 파트너 미팅 전까지 무엇을 준비해야 하는지 명확히 정리한다.
2. 국내 웹 버전에서 앱 중심 구조로 확장하면서, 한국/일본 서비스를 공통 코어 기반으로 관리하기 위한 개발 운영 원칙을 정한다.

---

## 2. 지금 기준의 핵심 판단

### 2-1. 행사 대응 원칙
- SusHi Tech는 단순 전시보다 **business matching / collaboration opportunity** 성격이 강하다.
- 따라서 일본 완제품을 들고 가는 것보다, **한국에서 검증 중인 코어 제품 + 일본 현지화 가능한 구조**를 보여주는 것이 더 중요하다.
- 일본 파트너는 “기능 수”보다 아래를 먼저 볼 가능성이 높다.
  - 일본 실무에 맞는가
  - 기존 관리 프로세스에 붙는가
  - 다국어/역할 분리가 되는가
  - 데이터/정책 분리가 가능한가

### 2-2. 제품 구조 원칙
- **코어는 하나, 서비스는 둘**로 간다.
- 즉,
  - Master Core: 공통 엔진
  - Korea Layer: 한국 템플릿/정책/요금제
  - Japan Layer: 일본 템플릿/정책/파트너 구조
- 처음부터 앱/DB를 완전히 별도 개발하는 것은 비효율적이다.
- 그러나 약관, 템플릿, 데이터 운영 정책, 리포트 구조는 국가별 분기를 전제로 해야 한다.

## 3. SusHi Tech 전까지 준비할 체크리스트 10개

### 3-1. 제품/데모
1. **Master Core 구조도 1장**
   - 촬영
   - 체크리스트
   - 비교
   - 무결성 검증
   - 리포트
   - 역할/권한
   - Export/API

2. **Korea / Japan Layer 분기 구조도 1장**
   - 한국: 주거/상가 템플릿, 한국어 리포트, 한국 정책
   - 일본: 주거/상가 템플릿, 일본어/영어 출력, 일본 정책

3. **일본 주거용 데모 템플릿 1개**
   - Move-in checklist
   - Room-by-room capture
   - Before/after compare
   - Responsibility tag
   - Export report

4. **일본 상가/오피스용 개념 템플릿 1개**
   - handover condition
   - restoration scope note
   - issue tag
   - stakeholder review

5. **다국어 리포트 샘플 1개**
   - KR/EN/JP 중 최소 2개 언어 버전
   - 동일 데이터가 언어만 바뀌어 출력되는 형태

### 3-2. 영업/파트너 대응
6. **일본 파트너에게 설명할 3개 use case 정리**
   - 주거 입주 전 기록
   - 주거 퇴거 전 비교 및 확인
   - 상가 퇴점 원상회복 범위 협의

7. **파트너 요청사항 문서 1장**
   - 어떤 파트너를 찾는지
   - 관리회사 / 중개사 / 보증회사 / 공사업체 중 누구와 PoC 하고 싶은지
   - 공동실증 범위

8. **API 또는 Export 명세 초안**
   - JSON export 항목
   - PDF report export
   - image package export
   - future API roadmap

### 3-3. 법무/운영
9. **국가별 운영 정책 초안 1장**
   - 국가별 약관/개인정보 처리방침 분리 원칙
   - 국가별 템플릿 분리 원칙
   - 데이터 저장/이전 정책 검토 포인트

10. **향후 로드맵 1장**
   - Phase 1: 한국 앱화 + 공통 코어 정리
   - Phase 2: 일본 주거용 템플릿/리포트 대응
   - Phase 3: 일본 상가/오피스 파트너 PoC
   - Phase 4: API/연동 확장

## 4. 개발 우선순위

### 4-1. 지금 바로 개발할 것

#### A. 템플릿 엔진
- 공간 유형별 템플릿 분기
  - 주거
  - 상가/오피스
- 국가별 템플릿 분기
  - 한국
  - 일본
- 필수/선택 항목 설정
- 체크리스트 버전 관리

#### B. 리포트 엔진
- PDF 출력
- 공유 링크 출력
- 다국어 라벨 출력
- 항목별 사진/메모/음성 연결
- 비교 결과 표시
- 책임 태그 표시

#### C. 증빙 엔진
- 원본 해시 생성
- 시간 기록
- 작성자/수정자 로그
- export용 패키지 생성
- 첨부자료 묶음 구조

#### D. 비교 엔진
- 입주 전/퇴거 후 항목 매칭
- 동일 구역 재촬영 비교
- 변경 포인트 하이라이트
- 차이 메모/태깅

#### E. 역할/권한 엔진
- 관리자
- 현장점검자
- 임대인/오너
- 임차인/테넌트
- 외부 검토자

### 4-2. 설계만 해두고 후순위로 미룰 것
- 360 카메라 연동
- 지도 기반 동선 최적화
- 자동 스케줄링
- AI 하자 자동탐지 고도화
- 외부 공사업체/견적 시스템 직접 연동

## 5. 앱으로 갈지, API로 갈지

## 5-1. 권장 구조

### 한국
- **모바일 앱 중심**
- 웹 콘솔 보조
- API는 후순위

이유:
- 한국은 현장 촬영 → 비교 → 보고서 생성 흐름이 핵심
- 사용자가 직접 폰으로 기록하는 가치가 큼
- 영업 메시지도 앱 기반이 직관적임

### 일본
- **현장 앱 + 웹 콘솔 + Export/API 대응**
- 단독 앱 판매보다 파트너 연동형 B2B 구조를 우선 고려

이유:
- 일본은 기존 부동산 DX 서비스/관리 시스템과 연결되는 구조가 설득력이 높음
- 현장 담당자와 관리회사/본사 역할이 분리될 가능성이 큼
- 파트너사가 “우리 시스템에 붙을 수 있는가”를 먼저 물을 가능성이 높음

## 6. 권장 제품 아키텍처

```text
[Mobile App]
  - 현장 촬영

  - 메모/음성/사진 첨부
  - 오프라인 저장
  - 업로드 동기화

[Core Backend]
  - 공간/항목 모델
  - 템플릿 엔진
  - 비교 엔진
  - 무결성 엔진
  - 리포트 엔진
  - 역할/권한 엔진
  - Export/API layer

[Admin Web Console]
  - 사건 조회
  - 리포트 관리
  - 템플릿 관리
  - 사용자/조직 관리
  - 국가별 설정 관리

[Country Layer]
  - Korea config
  - Japan config

```

## 7. 국내 웹 버전에서 앱 버전으로 전환할 때의 관리 원칙

### 7-1. 흔한 실패 패턴
- 웹 화면을 그대로 앱으로 옮김
- 현장 UX를 고려하지 않음
- 촬영/비교/리포트보다 메뉴 구조를 먼저 만듦
- 국가별 분기 요구를 하드코딩으로 처리함

### 7-2. 권장 전환 원칙
- 앱은 “기록 생산용”으로 설계한다.
- 웹은 “관리/검토/운영용”으로 설계한다.
- 공통 로직은 백엔드와 공통 도메인 모델에 둔다.
- 국가별 차이는 템플릿/설정/출력층으로 밀어낸다.

### 7-3. 앱에서 가장 중요한 사용자 흐름
1. 사건 생성
2. 자산 유형 선택 (주거 / 상가)
3. 국가/템플릿 선택
4. 공간별 촬영
5. 항목 체크 및 메모
6. 누락 경고 확인
7. 업로드 및 무결성 기록
8. 리포트 생성/공유

## 9. 실제 개발 관리 방식 제안

### 9-1. 트랙 분리
- **Track A: Master Core 개발**
- **Track B: Korea App 전환**
- **Track C: Japan Pilot 준비**

### 9-2. 스프린트 운영
- 2주 단위 스프린트
- 각 스프린트 목표는 “기능 개발”보다 “사용 시나리오 완성” 기준으로 잡는다.

예시:
- Sprint 1: 사건 생성 ~ 체크리스트 입력
- Sprint 2: 사진/음성/메모 저장 + 무결성
- Sprint 3: 전/후 비교
- Sprint 4: 리포트 출력
- Sprint 5: 국가/템플릿 분기
- Sprint 6: 일본 주거용 데모

### 9-3. 티켓 분류
- Core
- Mobile UX
- Report
- Country Config
- Integration
- Legal/Policy
- QA

### 9-4. 의사결정 원칙
- 모든 신규 기능은 먼저 아래 3개 중 어디에 속하는지 분류한다.
  1. 공통 코어인가?
  2. 한국 전용인가?
  3. 일본 전용/파일럿용인가?
- 분류가 안 되면 개발 보류

## 11. 개발팀 논의용 핵심 질문
1. 현재 웹 버전에서 재사용 가능한 도메인/로직은 무엇인가?
2. 앱 전환 시 촬영/오프라인/업로드 구조를 어떻게 설계할 것인가?
3. 템플릿 엔진을 하드코딩이 아니라 설정 기반으로 만들 수 있는가?
4. 리포트 엔진을 국가/언어별로 분기 가능하게 만들 수 있는가?
5. 무결성/해시/로그 구조는 어디서 어떻게 생성하고 검증할 것인가?
6. 일본 파트너에게 제공할 export는 어떤 포맷이 적절한가?
7. 사용자/조직/권한 구조를 B2B 기준으로 확장 가능한가?
8. 한국 릴리스와 일본 파일럿 릴리스를 feature flag로 나눌 수 있는가?

## 12. 최종 결론
- 스시테크에는 일본 완성품이 아니라 **공통 코어 + 일본 현지화 가능 구조**를 들고 가는 것이 맞다.
- 제품 전략은 **코어 하나, 국가별 서비스 둘**로 간다.
- 한국은 앱 중심, 일본은 앱 + 웹콘솔 + Export/API 대응 구조가 적합하다.
- 지금 당장 필요한 개발은 화려한 기능이 아니라 **템플릿 엔진, 리포트 엔진, 비교 엔진, 무결성 엔진, 권한/역할 구조**다.
- 내부 개발관리는 기능 목록이 아니라 **사용 시나리오, 국가 분기, 공통 코어 재사용** 기준으로 운영해야 한다.
